# Офлайн-обновления MOKKO CRM

Раздел `/updates` позволяет администратору загрузить ZIP-пакет, который заменит
файлы, добавит модуль и выполнит SQL-миграцию — без доступа к FTP и без
переустановки системы. Всё делается на сервере: пакет проверяется, файлы и БД
резервируются, при ошибке изменения откатываются.

> Код пакета выполняется с правами веб-сервера. Это такой же уровень доверия,
> как у FTP/SSH. Устанавливайте только свои сборки и храните резервные копии.

## Что есть в разделе

- загрузка ZIP с проверкой размера, путей, расширений и контрольных сумм;
- предпросмотр: версия, тип, список файлов, наличие SQL, предупреждения;
- установка с режимом обслуживания и дампом БД;
- журнал операций и откат к предыдущему состоянию;
- модули: установка, включение/выключение, удаление;
- необязательная HMAC-подпись пакетов.

## Формат пакета

В корне архива обязателен `mokko-update.json`:

```json
{
  "id": "mokko-1.1.0",
  "title": "MOKKO CRM 1.1.0",
  "version": "1.1.0",
  "type": "update",
  "requires": "1.0.0",
  "description": "Исправления и доработки",
  "sql": "sql/upgrade.sql",
  "delete": ["old/file.php"],
  "files": {
    "api/crm.php": "<sha256>",
    "js/panel.js": "<sha256>"
  }
}
```

Поля:

| Поле | Обязательно | Значение |
|---|---|---|
| `id` | да | латиница, цифры, `.`, `_`, `-`; 3–64 символа |
| `version` | да | `1.2.3` (допустимы суффиксы `-beta.1`) |
| `type` | да | `update` — ядро, `module` — модуль |
| `module` | для module | код модуля: `a-z`, `0-9`, дефис |
| `title` | нет | название для журнала |
| `requires` | нет | минимальная версия ядра |
| `sql` | нет | путь к `.sql` внутри архива |
| `delete` | нет | файлы, которые нужно удалить |
| `files` | нет | карта `путь: sha256`; сборщик заполняет сам |

`files` можно не указывать — тогда сервер посчитает хеши сам и покажет
предупреждение. Сборщик всегда добавляет `files`, это надёжнее.

### Что попадает на сервер

- файлы из архива, кроме `mokko-update.json`, `mokko-update.sig` и SQL-файла;
- SQL-файл **не копируется** в проект: он распаковывается во временный каталог
  и выполняется оттуда;
- `delete` удаляет перечисленные файлы (они тоже попадают в резервную копию).

### Ограничения

Запрещено пакетам:

- писать в `storage/`, `setup/`, `.git/`;
- менять `config/db_local.php`, `config/license.php`, `config/installed.lock`,
  `config/version.php`, `config/update.secret`, `config/maintenance.flag`,
  `config/updates.disabled`;
- содержать `.htaccess`, `.env`, `phar`, `cgi`, `exe`, `sh` и подобные файлы;
- выходить за пределы проекта (`../`), использовать абсолютные пути и symlink;
- для `type=update` — трогать `modules/` (модули ставятся отдельным пакетом);
- для `type=module` — писать вне `modules/<код>/`.

Разрешённые расширения: `php, js, css, scss, json, html, htm, svg, png, jpg,
jpeg, webp, gif, ico, woff, woff2, ttf, otf, eot, md, txt, map, xml, csv,
webmanifest`. SQL разрешён только как `manifest.sql`.

## Сборка пакета

Исходники повторяют структуру проекта:

```
src/
  mokko-update.json
  api/crm.php
  js/panel.js
  css/theme.css
```

Сборка:

```powershell
C:\xampp\php\php.exe tools\build-update.php src dist\mokko-1.1.0.zip
```

Сборщик:

- проверяет манифест;
- считает SHA-256 каждого файла и записывает в `files`;
- исключает `config/db_local.php`, `config/installed.lock`, `storage/`, `.git/`,
  `mokko-update.sig`, `setup/`;
- не даёт смешивать `update` и `modules/`.

Полезные флаги:

```powershell
# перезаписать существующий архив
--force

# подписать пакет ключом сервера
--secret=<64 hex>

# собрать без подписи, даже если ключ есть
--no-sign
```

## Установка

1. Откройте `http://<сайт>/updates` под администратором.
2. Перетащите ZIP в область загрузки.
3. Проверьте предпросмотр: версию, файлы, SQL, предупреждения.
4. Оставьте включёнными «режим обслуживания» и «дамп БД».
5. Поставьте галочку «Понимаю, что пакет изменит файлы» и нажмите «Установить».

Что происходит на сервере:

1. повторная проверка архива (файл мог измениться после предпросмотра);
2. проверка версии: старая версия ядра запрещена, та же — только с галочкой
   «Переустановить»;
3. резервная копия каждого заменяемого/удаляемого файла в
   `storage/updates/backups/<token>/files/`;
4. `mysqldump` в `storage/updates/backups/<token>/db.sql` (если есть SQL);
5. распаковка во `storage/updates/staging/<token>/` с проверкой SHA-256;
6. включение режима обслуживания (посетители получают 503);
7. замена файлов и удаление указанных в `delete`;
8. выполнение SQL-миграции;
9. запись новой версии в `config/version.php` (для `type=update`);
10. запись в журнал, выключение режима обслуживания.

При любой ошибке файлы восстанавливаются из резервной копии, а БД — из дампа
(если SQL уже начал выполняться). Режим обслуживания снимается.

## Откат

В истории у каждой успешной установки есть кнопка «Откатить».

- файлы возвращаются к состоянию до установки;
- файлы, добавленные пакетом, удаляются;
- удалённые пакетом файлы восстанавливаются;
- по желанию БД восстанавливается из дампа.

**Важно:** восстановление БД заменяет базу целиком — данные, созданные после
обновления, будут потеряны. Поэтому галочка «Восстановить БД» по умолчанию
выключена.

Если после обновления файлы правили вручную, откат откажется их перезаписывать.
Принудительный откат доступен отдельным подтверждением.

## Модули

Модуль — каталог `modules/<код>/` с `module.json`:

```json
{
  "title": "Лояльность",
  "version": "1.0.0",
  "description": "Бонусы и скидки",
  "bootstrap": "bootstrap.php"
}
```

`bootstrap.php` выполняется при каждом запросе и может регистрировать хуки:

```php
mokko_add_hook('panel.nav', function () {
    echo '<li><a href="#mod-loyalty">Лояльность</a></li>';
});

mokko_add_hook('panel.layers', function () {
    echo '<div class="layer" id="mod-loyalty">...</div>';
});
```

Доступные хуки:

| Хук | Где срабатывает |
|---|---|
| `app.boot` | после загрузки всех модулей |
| `panel.head` | в `<head>` панели (CSS модуля) |
| `panel.nav` | в меню панели |
| `panel.layers` | после экранов панели |
| `panel.footer` | перед `</body>` панели |

Выключение модуля создаёт `modules/<код>/.disabled`, файлы остаются на диске.
Удаление перемещает каталог в `storage/updates/removed/` — данные в БД не
трогаются, модуль можно вернуть вручную.

Пакет модуля собирается так же, но все файлы должны лежать в
`modules/<код>/...`, а в манифесте указывается `"type": "module"` и
`"module": "<код>"`.

## Подпись пакетов

Если в `config/update.secret` лежит 64 hex-символа, сборщик добавляет
`mokko-update.sig` — HMAC-SHA256 от байтов манифеста. Сервер:

- проверяет подпись, если файл есть;
- предупреждает, если ключ есть, а подпись отсутствует;
- отвергает пакет при неверной подписи.

Чтобы требовать подпись всегда, создайте `config/update.require_signature`
(достаточно пустого файла).

Ключ можно создать в разделе «Обновления» кнопкой «Создать ключ». Он
показывается один раз — сохраните его для сборщика и не публикуйте.

## Режим обслуживания и отключение

- `config/maintenance.flag` — включается на время установки. Если обновление
  упало, администратор видит сайт, остальные — 503; снять флаг можно кнопкой в
  разделе или удалив файл.
- `config/updates.disabled` — полностью запрещает API обновлений. Полезно на
  боевом сервере, где обновления ставятся только вручную.

## Права и требования

Веб-сервер должен иметь право записи на:

- `storage/` (создаётся автоматически);
- `config/` (дамп версии, maintenance.flag, update.secret);
- файлы проекта, которые заменяет пакет.

На Windows/XAMPP: сервис Apache обычно работает от `SYSTEM` и уже имеет доступ.
Если панель показывает «Каталог обновлений недоступен», выдайте права на
`storage/` и `config/` пользователю Apache.

Дополнительно:

- PHP 7.3+ с `zip`;
- `mysqldump`/`mysql` в `C:\xampp\mysql\bin` или в `PATH` — для дампа и отката
  БД. Без них установка с SQL остановится (можно продолжить без дампа,
  но это не рекомендуется);
- `proc_open` не должен быть отключён.

Для восстановления БД из дампа пользователю MySQL нужны права на
`CREATE DATABASE`/`DROP DATABASE` (дамп содержит `DROP DATABASE`). Если прав
нет, откат файлов сработает, а БД придётся восстанавливать вручную.

Лимит загрузки — 64 МБ (и не больше `upload_max_filesize`/`post_max_size`).
В `.htaccess` уже подняты значения до 64/72 МБ для mod_php. На PHP-FPM
увеличьте `upload_max_filesize` и `post_max_size` в php.ini.

## Если что-то пошло не так

- **«Не найден mysqldump»** — укажите путь в `PATH` или поставьте XAMPP-утилиты
  в `C:\xampp\mysql\bin`.
- **«Контрольная сумма не совпадает»** — архив изменён после сборки;
  пересоберите пакет.
- **«Файл запрещён к установке»** — проверьте путь: нельзя `setup/`, `storage/`,
  `config/db_local.php`, `.htaccess`, `modules/` для `update`.
- **«Резервная копия уже существует»** — этот пакет уже устанавливали;
  загрузите ZIP заново (токен новый) или удалите
  `storage/updates/backups/<token>/`.
- **Сайт показывает 503** — включён режим обслуживания. Откройте `/updates` под
  администратором и нажмите «Отключить» либо удалите `config/maintenance.flag`.

## Если сайт не открывается

Если пакет сломал `index.php` и раздел `/updates` недоступен, откатитесь из
командной строки — движок не зависит от фронт-контроллера:

```powershell
# список доступных откатов
C:\xampp\php\php.exe tools\rollback.php --list

# вернуть файлы
C:\xampp\php\php.exe tools\rollback.php <token>

# вернуть файлы и БД
C:\xampp\php\php.exe tools\rollback.php <token> --db

# игнорировать ручные правки файлов
C:\xampp\php\php.exe tools\rollback.php <token> --force
```

Запускайте от пользователя, которому принадлежат файлы проекта (на Linux —
владелец сайта или `www-data`), иначе не будет прав на запись.

## Резервные копии

Резервные копии обновлений лежат в
`storage/updates/backups/<token>/`:

```
db.sql        — дамп БД до установки (если был SQL)
files/...     — копии заменённых и удалённых файлов
state.json    — журнал действий и хеши
```

Каталог `storage/` закрыт от веб-доступа через `.htaccess` и rewrite в корневом
`.htaccess`. Не выкладывайте его в публичные бэкапы.

На Nginx (где `.htaccess` не работает) добавьте в конфигурацию сайта:

```nginx
location ^~ /storage/ { deny all; return 404; }
location ^~ /setup/   { deny all; return 404; }
```

`/setup/` после установки нужно удалить или закрыть в любом случае.
